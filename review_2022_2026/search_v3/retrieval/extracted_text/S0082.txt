DriftDroid: temporal behavioral drift analysis for 
android malware detection
Muhammet Tan  · Halit Bakır  · Eid Albalawi  · A. H. Abdul Hafez
Received: 26 June 2026 / Accepted: 24 September 2026
© The Author(s) 2026
Abstract
Android malware detectors often perform well under random or temporally mixed evaluation, yet deployed 
systems classify applications appearing after training. DriftDroid is a temporal behavioral drift measurement 
protocol for dynamic Android malware detection, not a new detector architecture: it measures how histori -
cal runtime-behavior evidence transfers to applications and explains performance decay. KronoDroid supplies 
14,348 tabular behavioral profiles and 10,000 event-sequence traces as the historical source domain; a balanced 
6,000-sample AndroZoo hold-out from 2024 onward is reserved for testing. Applications are represented with 
62 train-domain event tags and 165 aggregate features, evaluated across sequence and tabular probes without 
target-domain refitting. Although KronoDroid validation scores are high, temporal testing reveals degrada -
tion: the best sequence model reaches 0.7988 macro-F1 on AndroZoo, whereas the best tabular model reaches 
0.7010. The dominant tabular failure mode is benign-side drift, as recent benign applications increasingly 
exhibit network, file, cryptographic, SDK, and service behaviors historically correlated with malware. Thus, 
Android malware evaluation requires temporal hold-outs and representation-aware drift analysis. As secondary 
operational evidence, tabular tree ensembles recover with 600 labeled future-domain samples, closing 72–80% 
of the temporal performance gap, whereas sequence models provide stronger unadapted detection, while multi-
seed fine-tuning with a separate target-domain validation subset improves both sequence probes and reveals a 
non-monotonic adaptation response with greater seed/split sensitivity for BiLSTM.

Introduction
Mobile devices have become indispensable to daily life, with Android commanding approximately 74% of the 
global mobile operating system market1. This dominance, coupled with the platform’s open-source architecture, 
has made Android a primary target for malicious actors. According to Kaspersky’s 2023 Mobile Threat Report, 
over 33.8 million malware, adware, and riskware attacks were blocked on mobile devices, representing a 50% 
year-over-year increase. More than 1.3 million unique malicious installation packages were identified, of which

154,000 contained mobile banking Trojans. The threat remained active in the following reporting cycle: Kasper-
sky’s 2024 mobile threat analysis reported a 196% increase in Trojan-banker attacks on Android smartphones, 
from roughly 420,000 attacks in 2023 to 1.24 million in 2024 2. These escalating figures underscore the urgent 
need for robust long-term malware detection mechanisms capable of keeping pace with an increasingly sophisti-
cated threat landscape. The central difficulty is not only whether a model can separate malicious and benign appli-
cations in a curated benchmark, but whether it remains reliable when the Android ecosystem, malware families, 
platform APIs, and user-facing application behavior evolve after deployment.
A substantial body of work has addressed Android malware detection through classical machine learning and 
deep learning. Static detectors use permissions, API calls, intents, manifest declarations, opcodes, or bytecode-
derived representations to provide efficient pre-execution screening 3–5. Dynamic detectors execute applications 
and monitor runtime behavior such as system calls, API events, and network traffic, thereby capturing behaviors 
that may be hidden from static inspection6–9. Hybrid detectors combine static and dynamic evidence to improve 
coverage and robustness10–12. These lines of work have produced strong reported scores, but many studies still 
evaluate models using random splits or temporally mixed datasets, allowing future-like samples to influence 
training and validation. Under such protocols, high accuracy may reflect benchmark convenience rather than 
deployment readiness.
Recent research has shown that this evaluation gap is not a minor methodological detail. Early empirical studies 
warned that Android malware evaluation must respect time when measuring generalization13, and TESSERACT 
later demonstrated that spatial and temporal bias can substantially inflate malware-classification performance 
when train/test splits do not match realistic deployment constraints 14,15. KronoDroid was created specifically to 
support time-aware Android malware research by providing timestamped hybrid features over a broad historical 
period16. More recent surveys argue that Android malware detection is far from “mission accomplished”, identi-
fying outdated datasets, neglected concept drift, dynamic-data consistency, model security, and explainability as 
unresolved obstacles for long-term detectors17.
However, existing studies either focus on evaluation protocols or model adaptation, while lacking an explicit 
analysis of how runtime behaviors evolve over time and how such evolution affects detection performance. This 
paper therefore shifts the focus from simply proposing another dynamic detector to studying temporal drift in 
Android runtime behavior. DriftDroid is not a new detector architecture; it is a temporal behavioral drift measure-
ment protocol that uses existing classifiers as controlled probes to quantify and explain how runtime behavior 
evidence ages. We train on historical KronoDroid samples and reserve recent AndroZoo samples dated from 2024 
onward exclusively for testing in the primary source-only temporal evaluation18. Each application is executed in 
a controlled Genymotion-based environment, instrumented at runtime, and represented through both sequential 
behavioral tags and aggregate dynamic features. The objective is twofold: first, to measure how well behavioral 
detectors generalize from past to future samples; second, to explain how runtime behavior changes across time. 
In this framing, model performance is evidence of temporal generalization, while feature distributions, event 
sequences, and behavior-category prevalence explain the source of degradation.
Research questions
This study is organized around four research questions:

RQ1 Do runtime behavioral detectors trained on historical Android data temporally generalize to applications

RQ2 Which runtime behavior categories and feature distributions shift most from the historical source domain

Contributions
The principal contributions of this work are summarized as follows:
Unlike prior works that treat temporal shift as an evaluation artifact, this study explicitly models and explains 
behavioral drift in dynamic Android malware detection.
 ● Temporal generalization protocol. We formulate Android malware detection as a temporal generalization 
problem, use tabular and sequence-based detectors as controlled measurement instruments, and evaluate them 
under a strict historical-training and future-testing protocol with no future-domain information used during 
source-model development.
 ● Behavior-centric instrumentation pipeline. We construct a dynamic analysis pipeline that represents runtime 
activity through 62 interpretable behavioral tags and 165 aggregate dynamic features derived from frequency, 
temporal, derived, and sequence-chain views.
 ● Cross-domain behavioral drift characterization.  We quantify and explain behavioral drift using Jensen–
Shannon divergence (JSD), entropy difference, category-level prevalence shifts, and feature-level distribu -
tional analysis, identifying which runtime behaviors age and why—in particular, the benign-side SDK and 
service inflation that collapses historically malware-specific aggregate signals.
 ● Secondary adaptation asymmetry study. As an operational follow-up to the drift analysis, we conduct ex -
ploratory adaptation experiments across all seven probes. For sequence probes, fine-tuning is repeated over six 
seeds using independent target-domain validation and untouched final-test splits. These secondary experiments 
suggest a data-efficiency asymmetry: tabular tree-ensemble probes close 72–80% of the temporal performance 
gap with 600 labeled future-domain samples, while sequence probes start from stronger unadapted baselines 
and improve under fine-tuning, but with non-monotonic BiLSTM sensitivity across seeds.

Related work
Android malware detection has evolved from static feature classification toward dynamic, hybrid, and sequence-
based learning. However, the central question for a deployable detector is no longer only which representation 
achieves the highest score on a fixed benchmark. A detector must also remain reliable when applications, Android 
APIs, benign software practices, and malware behavior change over time. This section therefore reviews prior 
work around four connected themes: Android malware detection paradigms, temporal bias and realistic evalu -
ation, drift adaptation, and behavioral drift interpretation. Across these themes, we emphasize a recurring limi -
tation: much of the literature either improves detection accuracy, constrains evaluation, or adapts models after 
degradation, but does not explain the behavioral changes that make future samples difficult to classify.
Android malware detection paradigms
Static analysis remains attractive because permissions, manifest entries, API calls, intents, and bytecode fea -
tures can be extracted without executing an application. Permission- and API-based detectors scale well for 
pre-installation screening, but their evidence is vulnerable to obfuscation, packing, API evolution, and changing 
development practices3–5,19.
Dynamic analysis instead observes runtime behavior such as system calls, API traces, network traffic, and 
resource interactions6–9. Recurrent, attention-based, and transformer models further exploit temporal order by 
treating API or behavioral logs as sequences 20–24, while hybrid approaches combine static and dynamic evi -
dence10–12. These representations improve conventional benchmark discrimination, but they usually treat the 
dataset as a fixed population and leave open whether dynamic and sequence signals remain stable years after 
training.
Recent malware-detection studies also emphasize that dataset preprocessing, feature representation, and fea -
ture selection materially affect model performance. Work on CLaMP and PE-header-based malware classifiers 
has used preprocessing pipelines, SVM preprocessing, MRMR ranking, Relief-F feature selection, and feed-
forward neural deep features to reduce feature overhead or improve static malware discrimination 25–29. These 
works are valuable for efficient static malware detection, whereas the present study asks a complementary ques-
tion: whether runtime behavioral evidence learned from a historical Android domain remains temporally reliable 
on recent Android applications.
Broader cybersecurity research further shows that ML-based defense is being extended to 5G-enabled IoT 
systems, privacy-preserving federated learning, and generative-AI risk assessment 30–32. These studies motivate 
the general need for adaptive and privacy-aware security analytics, but they do not replace Android-specific tem-
poral validation because mobile malware detectors face platform, SDK, family, and application-ecosystem drift.
Temporal bias and realistic evaluation
The temporal dimension has long been recognized as a threat to Android malware evaluation. Allix et al 13. 
showed that time-aware protocols are necessary because temporally mixed train/test splits can misrepresent 
deployment generalization. TESSERACT made this concern central by formalizing spatial and temporal con -
straints and showing that unrealistic splits inflate performance14; its extended analysis further confirms that high 
F1-scores do not settle malware classification when models decay under temporal and spatial shift15.
Realistic evaluation, however, does not by itself explain failure. A detector evaluated chronologically must 
classify applications that did not exist during training, and its errors may arise from changing runtime behavior 
rather than only weaker classification. KronoDroid supports time-aware analysis through timestamped Android 
features16, and recent timestamped or self-supervised Android malware studies likewise emphasize temporal veri-
fication33. The review by Guerra-Manzanares17 highlights neglected concept drift, outdated datasets, inconsistent

dynamic data, model security, and limited explainability. Thus, prior work establishes the evaluation problem, but 
not which runtime behaviors shift or how those shifts affect dynamic detectors.
Concept drift handling through online and active learning
Several studies address temporal degradation by updating detectors over time. DroidOL, CASANDRA, AndrO-
Det, and DroidEvolver use online, self-evolving, or pseudo-label-based strategies to adapt feature knowledge 
and classifiers as malware populations change34–37. These methods treat drift primarily as a model-maintenance 
problem: when the distribution changes, the detector must be refreshed.
A related line treats drift as uncertainty management. TRANSCEND and TRANSCENDENT compare new 
samples with the training distribution or reject uncertain predictions under drift 38,39. Recent Android-specific 
work extends this view with active learning, label delay, and streaming retraining40,41. These approaches are valu-
able for deployment, yet they mainly decide when and how to update a model. They do not directly identify which 
runtime behavior categories changed, how prevalence shifted, or whether sequence-level dynamics themselves 
drifted.
Representation robustness and behavioral drift analysis
A complementary line asks how to learn features that remain stable across time. APIGraph maps API evidence 
into semantic relations to reduce model aging 42, TIF targets temporal invariance by discouraging reliance on 
unstable discriminative features43, and BYOL-style self-supervised Android malware detection seeks robust rep-
resentations under timestamp-aware evaluation 33. Explainability-oriented robust feature selection, such as the 
LIME/SHAP analysis of Najibi and Bidgoly 44, similarly connects feature robustness with detector reliability, 
although without a strict historical-train/future-test behavioral drift protocol.
Forensic drift analysis provides the interpretive layer needed here. Zola et al45. argue that temporal shifts should 
be dissected through rolling evaluation, temporal aggregation, misclassification analysis, and feature inspection 
because performance decay alone does not explain why a model fails. Following this perspective, we com -
pare historical KronoDroid and recent AndroZoo runtime behavior through tag distributions, category frequen -
cies, sequence lengths, entropy, and prevalence changes. The gap addressed here is a dynamic, sequence-aware 
Android malware study that jointly evaluates future generalization and explains the behavioral drift responsible 
for it.
Materials and methods
Dynamic analysis infrastructure
Dynamic behavioral analysis of Android applications requires a controlled, reproducible execution environment 
that can process thousands of APKs at scale while maintaining clean system state between samples. We designed 
a distributed analysis pipeline built around four parallel Genymotion Android 8.0 emulator instances, each run -
ning ARM Translation support to faithfully emulate real-device behavior. The pipeline is composed of three 
tightly integrated layers: a shell-level orchestration framework, a Python-based analysis coordinator, and a Frida 
TypeScript instrumentation agent injected into the target process.
Parallel emulator orchestration
The protocol emphasizes controlled, repeatable, and fault-tolerant behavioral acquisition so that downstream 
learning is based on comparable runtime observations rather than execution artifacts 21,22,24. We use a parallel

emulator pool composed of independent Android virtual devices; each instance isolates one application at a 
time, enabling concurrent analysis while preventing cross-sample contamination. Applications are distributed 
across workers, and periodic emulator resets remove accumulated state such as residual processes, memory frag-
mentation, and cached artifacts. The orchestration framework monitors emulator health, recovers unresponsive 
instances, synchronizes APK assignment to avoid duplicate processing, and records checkpoints so interrupted 
runs can resume without redundant analysis. All samples are executed on the same Android 8.0 image to keep 
the measurement environment fixed across the historical and recent domains. This design improves longitudi -
nal comparability, but it also means that the reported drift should be interpreted as temporal behavioral transfer 
under a fixed analysis environment rather than as a clean separation between application-level concept drift and 
operating-system compatibility effects.
Per-APK analysis protocol
Each APK is analyzed under a deterministic protocol designed for reproducibility, isolation, and behavioral com-
parability. Before execution, the emulator is restored to a clean baseline; the target application is then installed 
and launched through its declared activity, falling back to a package-scoped Android Monkey launcher event 
when no standard entry point is available. Runtime monitoring uses process-level Frida attachment on unmodi -
fied APKs, avoiding repackaging and improving compatibility with real-world samples.
Instrumentation is deployed through a reusable precompiled agent, and behavioral data are collected during 
a fixed 120-second window. After installation, the application receives a 15-second stabilization interval; fol -
lowing attachment, instrumentation state is queried after a one-second warm-up and then polled every five sec -
onds through Frida RPC. To exercise UI- and broadcast-dependent behavior, a package-scoped Monkey process 
injects up to 500 UI events with an 800 ms throttle, while deterministic stimulation at 15 and 45 seconds sends an 
SMS-received broadcast, toggles screen state, and posts a test notification. These stimuli are class-independent, 
increasing behavioral coverage without injecting label-specific signals.
Timeout-aware monitoring and early termination handle non-responsive applications, anti-analysis delays, and 
instrumentation stalls. At the end of the window, collected behavior is atomically consolidated into the feature 
representation, the application is removed, and the emulator proceeds to the next sample. The pipeline records 
behavioral trace density and tag diversity but does not collect instruction-, method-, or basic-block-level code 
coverage. Consequently, the coverage-related analysis reported below is framed as a runtime-activity proxy for 
triggered monitored behavior, not as a substitute for full code-coverage instrumentation.
API instrumentation and feature extraction
Frida instrumentation agent
The instrumentation layer is explicitly behavior-centric: it groups runtime events into semantically defined secu-
rity-relevant categories and preserves their frequency, timing, and ordering simultaneously22,23. To capture fine-
grained runtime behavior, we design a behavior-centric instrumentation agent based on dynamic API hooking. 
The agent monitors a diverse set of Android API entry points spanning multiple behavioral categories, including 
dynamic code loading, network communication, cryptographic operations, file system access, inter-process com-
munication, and user privacy-sensitive actions, as summarized in Table 1.
The instrumentation strategy explicitly models semantically meaningful behavioral groups rather than only 
coarse aggregate system-call or network summaries. This enables the system to distinguish between functionally 
similar but contextually different activities, such as benign analytics logging versus privacy-invasive data col -
lection. The “benign SDK” category is a semantic grouping of instrumentation hooks associated with common 
third-party application services, including analytics and crash-reporting clients, advertising or attribution librar -
ies, social-sharing intents, media playback frameworks, legitimate notification posting, remote configuration,

cloud service integration, and authentication flows. The category is not treated as a ground-truth benign label 
for an application; rather, it records API behaviors that are commonly produced by mainstream SDK functional-
ity and can therefore become confounding aggregate evidence when such behaviors increase in recent benign 
applications. The resulting runtime vocabulary contains 62 interpretable behavioral tags that form the basis of 
the sequence modeling and behavioral drift analyses. While several recent transformer-based studies improve 
dynamic malware analysis through preprocessing, token normalization, or sequence classification, they generally 
remain focused on distinguishing malicious semantics from raw behavioral content; in contrast, we explicitly 
model benign SDK signals as a separate category to reduce confusion between legitimate analytics/advertising 
behavior and privacy-invasive activity with superficially similar API footprints22,24,46. Each intercepted API call 
contributes to three complementary representations. First, global counters track the frequency of behavior across 
categories. Second, first-occurrence timestamps capture temporal characteristics, enabling the analysis of early-
stage execution patterns. Third, all events are recorded in a structured sequential log, preserving ordering infor -
mation for downstream sequence modeling. To ensure robustness, instrumentation is designed to be non-intrusive 
and fault-tolerant: failures in individual instrumentation callbacks do not interrupt the analysis process. This 
guarantees stable data collection even in the presence of incomplete class loading or obfuscated code structures.
Burst behavior modeling
Traditional frequency-based features fail to capture short-lived but high-intensity execution phases commonly 
observed in malware, such as payload unpacking or rapid data exfiltration. To address this limitation, we intro -
duce a burst-based feature that measures the peak density of API activity within a sliding temporal window. This 
feature provides a compact representation of execution intensity, enabling the detection of transient but highly 
indicative behavioral spikes.
Data export
The instrumentation agent outputs a unified behavioral representation combining frequency-based, temporal, 
and sequential information. This includes aggregated event counts, timing features, burst characteristics, and the 
ordered API event sequence, forming the foundation for the downstream feature engineering pipeline.

lenge in sequence-based dynamic analysis is the imbalance between high-frequency and low-frequency behav -
ioral events. In practice, a small subset of APIs—such as reflection or network communication—can dominate

categories are proportionally represented within each execution trace. Importantly, this design preserves rare but 
diagnostically significant events while preventing noise saturation caused by repetitive API calls. As a result, the 
resulting sequence representation maintains both diversity and discriminative power, improving the model’s abil-
ity to capture meaningful behavioral patterns across applications. This design is particularly important for cap -
turing multi-stage attack patterns, where rare precursor events may otherwise be lost in dense execution traces.
Feature engineering pipeline
The feature engineering pipeline integrates four complementary views of runtime behavior: direct event intensity, 
higher-order derived semantics, temporal execution dynamics, and explicit sequence-chain abstractions22–24. Raw 
outputs produced by the instrumentation agent are transformed into a structured tabular representation through a 
multi-stage feature engineering pipeline. The exported tabular profile contains 165 numeric behavioral features 
and three metadata fields, organized into raw counters, derived features, temporal features, and sequence-based 
features (Table 2). This design captures not only the presence of behavioral signals, but also their intensity, tem-
poral characteristics, and contextual relationships.
Raw behavioral counters
The first group consists of direct API call frequencies aggregated across all monitored behavioral categories 
(Table 2). These features provide a coarse-grained view of application activity, capturing the overall intensity of 
operations such as dynamic code loading, cryptographic usage, network communication, file system interaction, 
and privacy-sensitive actions. While informative, raw counts alone are insufficient for distinguishing benign and 
malicious applications due to their sensitivity to execution duration and application complexity. Therefore, they 
serve as a foundational layer upon which more discriminative features are constructed.
Derived behavioral features
To overcome the limitations of raw frequency signals, we construct a set of derived features that capture higher-
level behavioral semantics (Table 2). These include composite behavioral scores, inter-category ratios, Boolean 
pattern indicators, and normalized activity measures. Composite scores aggregate related API calls into inter -
pretable behavioral dimensions such as network activity, persistence, stealth, and exfiltration. To mitigate bias 
introduced by varying execution lengths, selected features are normalized by session duration, enabling fair 
comparison across applications. Behavioral ratios further capture relationships between categories, providing 
invariance to absolute activity levels. In addition, Boolean pattern flags encode compound behavioral signatures 
that are difficult to capture through individual features alone, such as the co-occurrence of encoding and network 
transmission or the combination of privilege escalation and dynamic execution. This multi-view design is moti -
vated by the limitations of raw-count and sequence-only modeling: frequency-based approaches ignore temporal 
context, whereas pure sequence models underutilize stable aggregate behavioral evidence unless it is explicitly 
encoded22,47. Finally, rate-based and log-transformed features are introduced to stabilize high-variance distribu -
tions and improve robustness for gradient-based learning models.

Temporal features
The third group captures the temporal dynamics of application behavior (Table 2). These features are derived 
from the timing of first-occurrence events and encode when specific behaviors emerge during execution. Early-
stage activity is particularly informative in malware detection, as malicious applications often trigger payload 
execution shortly after launch. To capture this phenomenon, we include early-activity indicators, inter-event 
timing relationships, and ordering constraints between behavioral categories. These timing-based features are 
highly discriminative within the source domain; however, as the feature-group ablation reveals, their absolute 
timing patterns can overfit to the historical behavioral cadence and reduce temporal transfer performance when 
the target domain exhibits different API-invocation timing—a subtlety that is not visible without an explicit tem-
poral evaluation protocol. Additionally, session-level indicators such as burst intensity and execution duration 
are incorporated to detect anomalous runtime patterns, including stalling behavior or delayed execution used to 
evade sandbox analysis.

Sequence-based behavioral features
The final group extracts higher-order behavioral patterns from the sequential API event log (Table 2). Rather than 
relying solely on token sequences for downstream models, we explicitly encode structured interaction patterns 
between events. These features capture ordered co-occurrence relationships, such as data access followed by 
network transmission or persistence setup preceding execution. Such patterns are particularly indicative of multi-
stage attack workflows and cannot be effectively represented through isolated counters or timestamps. We further 
incorporate chain-level statistics, including occurrence counts and timing of first appearance, enabling the model 
to reason about both the presence and progression of complex behavioral sequences.
Dual-format output
The pipeline generates two complementary output formats per analysis run to preserve both structured summaries 
and fine-grained behavioral dynamics.
Tabular behavioral profiles
The extracted tabular features provide a fixed-length behavioral profile for each analyzed APK, supporting gra -
dient-boosted tree evaluation and other lightweight tabular baselines. Each APK is represented by 168 columns, 
consisting of 165 numeric behavioral features and three metadata fields. This representation captures stable 
aggregate, temporal, and derived behavioral characteristics regardless of execution length.
Event-sequence traces
In parallel, a sequence-based representation is constructed, preserving the ordered runtime event trace along with 
session metadata. This representation supports sequence-based models, particularly transformer architectures 
that rely on contextual relationships between events. The current sequence pipeline retains the available event 
traces and pads or truncates event streams dynamically during batching, using a maximum sequence length of 
256 events. Very short execution traces are treated as low-context observations during modeling rather than 
removed from the tabular feature space, since aggressive sequence filtering can bias the dataset toward highly 
active applications. By preserving both tabular and sequential views, the pipeline enables complementary model-
ing of global behavioral patterns and temporal dependencies.
Detection models for temporal evaluation
The central contribution of this work is the temporal and behavioral drift analysis, not a new classifier architec -
ture. We therefore use representative sequence and tabular classifiers as measurement instruments for evaluating 
how different behavioral representations generalize from historical to future applications. All model selection, 
vocabulary construction, preprocessing, scaling, and threshold choices are performed only within the Krono -
Droid source domain before applying the trained models to the AndroZoo temporal hold-out.
Sequence-based probes
The sequence experiments use the ordered runtime event trace as input. Each event is mapped to a train-only 
behavioral vocabulary of 62 tags (Table 3), and traces are padded or truncated to a maximum length of 256 
events. Two sequence probes are evaluated. The BiLSTM captures bidirectional local and medium-range tem -
poral dependencies in event order, while the Transformer encoder captures longer-range contextual interactions

Tabular behavioral probes
The tabular experiments use the 165-dimensional behavioral feature vector after excluding package name, label, 
and timestamp metadata. The tabular probes cover both classical and neural model families: logistic regression as 
a linear reference, random forests, extremely randomized trees, and XGBoost as tree-based baselines for hetero-
geneous behavioral counts and ratios, and an MLP as a neural tabular baseline. These models are included to test 
whether aggregate behavioral profiles are more or less temporally stable than ordered sequence traces.
Evaluation models

Datasets
The study is positioned as a temporal generalization and behavioral drift analysis rather than an online-learning 
or continual-adaptation benchmark. KronoDroid is used as the historical source domain, while recent AndroZoo 
applications are reserved as a future-domain temporal hold-out. The completed AndroZoo target set is used as a 
balanced 6,000-application temporal hold-out dated from 2024 onward, with 3,000 malware and 3,000 benign 
samples (Table 5). Figure 1 summarizes the completed KronoDroid source-domain composition: 14,348 dynami-
cally analyzed tabular profiles and 10,000 event-sequence traces with valid runtime traces. An additional 147 
benign tabular profiles are retained as reserve samples and are not included in the balanced temporal evaluation.
The completed KronoDroid data are split only within the historical domain for model development. For tabu-
lar experiments, 12,195 applications are used for training and 2,153 for validation, preserving the near-balanced 
label ratio. For sequence experiments, the balanced 10,000-application trace subset is split into 8,500 training and 
1,500 validation applications. V ocabulary construction, feature scaling, model selection, and thresholding are all

KronoDroid provides temporally diverse historical samples spanning Android ecosystem evolution from 2008 
to 202016, whereas the AndroZoo split introduces more recent benign and malicious applications that better reflect 
contemporary SDK usage patterns and current malware behaviors. Candidate AndroZoo samples are selected

and VirusTotal consensus metadata were frozen in May 2026 before feature extraction. Malware candidates are 
restricted to applications dated 2024 or later and flagged as malicious by at least three VirusTotal engines. Benign 
candidates are restricted to applications dated 2024 or later with zero VirusTotal malicious detections. Samples 
with low-positive or otherwise ambiguous VirusTotal evidence are excluded from the temporal hold-out to reduce 
label noise. For the secondary adaptation analysis, the frozen AndroZoo target set is partitioned into disjoint 
adaptation, validation, and final-evaluation subsets, as detailed in Section Exploratory drift-aware adaptation.

To prevent data leakage, we perform cross-source deduplication before feature extraction and model training.

duplicate samples are removed prior to split construction. We additionally verify package identifiers to detect 
repeated applications with different collection metadata. This procedure ensures that no identical APK appears 
in both the training/validation pool and the held-out temporal evaluation set. A lightweight Python-based pre -

All APKs undergo dynamic analysis as described in the per-APK analysis protocol and API instrumentation

repeated instrumentation timeouts are recorded in the failure log and excluded from the final dataset. Deduplica-
tion and exclusion are completed before model fitting to ensure that downstream evaluation reflects only valid

Source-domain statistical characterization
Before evaluating temporal drift against AndroZoo, we characterize the completed KronoDroid source domain to 
establish the behavioral quantities that will later be compared across time. This characterization is not presented 
as the main drift result; rather, it defines the measurement layer for the future historical-versus-recent comparison. 
Event-trace length already shows strong class-conditional structure: benign applications contain a median of 18 
events per trace (mean 31.6, 95th percentile 107), whereas malware contains a median of 50 events (mean 61.6, 
95th percentile 168) (Fig. 2). A Mann–Whitney U test and a two-sample Kolmogorov–Smirnov test both reject 
equality of the length distributions ( 𝑝𝑝≪ 0.001, Cliff’s 𝛿𝛿 𝛿 𝛿𝛿𝛿𝛿𝛿), indicating a large shift toward longer and denser 
malware traces.
At the behavioral-category level, malware exhibits higher application-level prevalence for surveillance and 
privacy access (80.6% versus 17.0%), file operations (78.3% versus 39.8%), cryptography (71.7% versus 37.4%), 
network and C2 behavior (85.3% versus 54.0%), and persistence or privilege-related behavior (44.0% versus 
19.3%) (Fig. 3). These differences are statistically significant under chi-square tests after category aggregation. 
The same prevalence estimates are then computed for the recent AndroZoo hold-out and compared using effect 
sizes and multiple-testing-aware significance analysis, allowing the paper to explain not only whether perfor -
mance changes, but which runtime behaviors changed.
The tabular behavioral profiles provide a complementary view of this separation (Fig. 4). Device-identifier 
access is observed in 57.2% of malware but only 3.4% of benign applications, while surveillance, network, exfil-
tration, stealth, and file-write/read behaviors also show large prevalence gaps. These source-domain differences 
are useful for detector training, but they are also exactly the type of evidence that can become unstable over time. 
The drift evaluation will therefore report feature-prevalence changes, Jensen–Shannon divergence, entropy dif -
ference, and category-level effect sizes between KronoDroid and the completed AndroZoo hold-out.

Cross-domain behavioral drift characterization
The completed AndroZoo hold-out enables a direct comparison between the historical KronoDroid source domain 
and recent applications collected from 2024 onward. The most visible shift appears in runtime trace density. In 
KronoDroid, malware traces are substantially longer than benign traces, with medians of 50 and 18 events, 
respectively. In the recent AndroZoo hold-out, this class-conditional gap nearly disappears: benign and malware 
traces have median lengths of 96 and 95.5 events, respectively (Fig. 5). This indicates that trace length alone is 
not a stable malware indicator across time. Recent benign applications generate denser runtime behavior, likely 
due to contemporary SDKs, authentication libraries, cloud services, telemetry, file-cache operations, and push or 
notification mechanisms.
To further assess whether monitored behavior is actually triggered during the fixed execution window, Table 6 
reports runtime-activity proxy statistics computed from the event-sequence logs. These statistics do not measure 
code coverage; rather, they summarize how many monitored events and behavioral tags were observed within the 
120-second analysis window and during the first 30 seconds of execution.

Experimental setup
The experimental protocol uses KronoDroid for model development and reserves AndroZoo for temporal out-
of-distribution testing. Within KronoDroid, training and validation are stratified, while all preprocessing deci -
sions that can leak distributional information are fit only on the training split. For tabular experiments, metadata 
fields are excluded from model input, yielding 165 behavioral dimensions. The tabular evaluation uses repre -
sentative classical and neural probes, including logistic regression, random forests, extremely randomized trees, 
XGBoost, and an MLP. Each complete preprocessing-and-model pipeline is fit only on KronoDroid and then 
applied unchanged to the balanced AndroZoo temporal hold-out.

Reproducibility details
The primary source-only temporal evaluation uses a fixed random seed of 42 and a stratified 85/15 KronoDroid 
train/validation split. In that evaluation, the frozen AndroZoo set is used only once for temporal inference and 
drift characterization; it is not used for preprocessing, source-domain model selection, vocabulary construc -
tion, threshold tuning, or early stopping. The separate sequence-adaptation analysis re-partitions the same frozen 
AndroZoo set over six random seeds (11, 22, 33, 42, 44, and 55) into disjoint adaptation, validation, and final-test 
subsets, and fine-tunes only the sequence probes under that secondary protocol. Binary decisions in the source-
only temporal evaluation use a fixed 0.5 malware-probability threshold, so the reported false-positive and false-
negative rates reflect deployment-style transfer rather than target-domain optimization.
Table 7 summarizes the main experimental settings. Sequence traces are capped at 256 events because this 
length preserves the majority of source-domain traces, including the 95th percentile of KronoDroid malware 
traces, while bounding memory and training time. Unseen AndroZoo event tags are mapped to an unknown 
token, preserving the strict train-past/test-future protocol. For tabular models, median imputation is fit on the 
KronoDroid training split; robust scaling is used only for scale-sensitive logistic regression and MLP probes, 
while tree-based models use unscaled imputed features. Hyperparameters are intentionally standard and modest 
rather than exhaustively tuned, because the models are used as representation probes for drift evaluation rather 
than as a new detector architecture. The table also documents the settings most likely to affect replication: the 
fixed threshold, train-only vocabulary, neural optimization parameters, tabular preprocessing, and tree-ensemble 
sizes. Together with the dataset composition in Table 5, these settings define the complete experimental protocol 
used to produce the results in Table 8.

Results and discussion
The central empirical message is that temporal degradation is primarily a benign-side behavioral convergence 
problem, not simply malware evolution. Table 8 reports the completed source-domain validation and temporal 
hold-out results for both representation families. The high KronoDroid validation scores show that the probes can 
learn discriminative historical runtime patterns. However, every model degrades on the recent AndroZoo hold-
out, confirming that source-domain validation alone overestimates future-domain reliability.
The temporal degradation is not uniform across model families. The Transformer obtains the strongest Krono-
Droid validation ROC-AUC (0.9905) and remains slightly better ranked by AndroZoo ROC-AUC (0.8525), but 
its fixed-threshold malware recall degrades sharply on the temporal hold-out, producing a false-negative rate of 
30.2%. The BiLSTM has a lower AndroZoo ROC-AUC (0.8371), yet it provides a more balanced fixed-threshold 
decision profile, with higher AndroZoo macro-F1 (0.7988 versus 0.7746) and a substantially lower false-negative 
rate (19.4%). This change in model ordering under temporal evaluation reinforces the paper’s central point: 
source-domain validation is insufficient for selecting a detector intended for future samples.
The tabular probes show an even stronger representation-level shift. On KronoDroid validation, the strongest 
tree-based models are competitive with the sequence probes: XGBoost, Random Forest, and Extra Trees all reach 
macro-F1 values around 0.953–0.954 and ROC-AUC values above 0.977. On the AndroZoo hold-out, however, 
the best tabular macro-F1 is 0.7010 for XGBoost, and the remaining tabular probes fall between 0.5869 and 
0.6446. The main failure mode is not an inability to detect malware; Random Forest, Extra Trees, and MLP keep 
false-negative rates near 10%. Instead, they classify many recent benign applications as malware, with false-
positive rates between 57.4% and 62.2%. This pattern is consistent with the dataset-level drift analysis: mod -
ern benign applications contain more network, file, cryptographic, SDK, and service behaviors that historically 
served as malware-correlated aggregate signals.

67.5%, the largest degradation across any ablation condition. Conversely, using only Raw Counters (79 features) 
achieves macro-F1 0.705, which is higher than the full 165-feature model. This confirms that raw API call counts 
are the primary carrier of temporally stable discriminative signal.
Second, Temporal Features (first-occurrence timestamps and inter-event deltas) are temporally fragile: remov-
ing them improves AndroZoo macro-F1 by 2.4 pp (0.696 →0.720) and reduces FPR from 42.2% to 40.1%. This 
counter-intuitive result indicates that absolute timing patterns learned from KronoDroid overfit to the historical 
behavioral cadence of the source domain; modern applications trigger the same APIs at different intervals, mak-
ing timing-based features negative transfer signals under temporal evaluation.
Third, sequence-chain tabular features are perfectly redundant: removing them produces no change whatso -
ever (0.000 pp), and using them alone fails entirely (Krono macro-F1 0.334, FNR 100%), because ordered-chain 
flags are too sparse to train a useful XGBoost decision boundary without the supporting count context. This nega-
tive result indicates that the current chain design acts mainly as a sparse hand-engineered annotation layer rather 
than as an independent representation. We therefore do not interpret the sequence-chain tabular block as a useful 
contribution in its present form; future versions should either remove these flags from the tabular feature set or 
replace them with denser learned n-gram, motif, or sequence-embedding summaries that preserve order without 
collapsing into near-constant binary indicators.
Taken together, the ablation reveals that the temporal degradation of tabular probes is dominated by raw behav-
ioral count drift—the benign-side SDK and service inflation that raises API-count profiles for recent benign apps 
toward historical malware baselines. Timing-based engineered features amplify this fragility rather than mitigat-
ing it, suggesting that future tabular representations for temporally robust Android malware detection should 
prioritize drift-stable raw behavioral counts over complex temporal derivations.

Exploratory drift-aware adaptation
The preceding sections constitute the primary contribution of the paper: measuring and explaining temporal 
behavioral drift under a strict historical-to-future protocol. This secondary analysis evaluates three lightweight 
adaptation strategies across all five tabular probes and both sequence models to examine how representation 
families respond when limited recent-domain evidence is available.
Drift-feature exclusion. Tabular models are retrained on KronoDroid after removing the top- K benign-side 
JSD features (𝐾𝐾∈{ 10, 20, 30}), requiring no future-domain labels.
Conservative threshold recalibration. Source-trained models are evaluated at elevated decision thresholds 
(𝑡𝑡∈{ 0.70, 0.80}) without parameter refitting. These sweeps are post-hoc operating-point diagnostics, not deploy -
ment-time calibration rules.
Few-shot supervised retrain or fine-tune. A stratified 5% or 10% subset of AndroZoo is used as labeled 
adaptation evidence. Tabular probes add this subset to KronoDroid and retrain from scratch; sequence probes 
fine-tune the KronoDroid checkpoint. For sequence probes, the protocol reserves an independent 10% AndroZoo 
validation subset for early stopping and leaves the remaining future-domain subset untouched for final testing. 
Consequently, the 5% and 10% adaptation conditions use final-test subsets of different sizes after the fixed valida-
tion carve-out, so non-monotonic differences should be interpreted jointly as adaptation-size and split-sensitivity 
effects rather than as a purely sample-size-driven trend. We repeat this fine-tuning protocol over six random seeds 
(11, 22, 33, 42, 44, and 55) and report mean ± standard deviation. These seeds affect only the AndroZoo adapta-
tion/validation/final-test re-partitions and fine-tuning stochasticity; the KronoDroid source checkpoints are fixed 
and are not retrained over multiple seeds.
Upper-bound estimates. Tabular upper bounds are 5-fold cross-validation results on the balanced AndroZoo 
hold-out; sequence upper bounds use 80% AndroZoo fine-tuning, 10% validation, and 10% untouched final 
testing, repeated over the same six seeds. Tables 14, 15, and 16 report macro-F1 with FPR in parentheses where 
applicable.
Tabular probe results (Table 14). XGBoost is the strongest tabular baseline (macro-F1 0.701, FPR 44.0%) 
and responds most aggressively to supervised adaptation: 300 labeled future-domain samples raise macro-F1 to 
0.847 and reduce FPR to 15.5%, while 600 samples raise macro-F1 to 0.878 and reduce FPR to 10.3%, closing 
approximately 80% of the gap to the 5-fold CV upper bound (0.922). Drift-feature exclusion does not consistently 
help XGBoost because the most-drifted features remain discriminative; thresholding at 𝑡𝑡 𝑡 𝑡𝑡𝑡𝑡 lowers FPR to 
36.8% with little macro-F1 change but higher FNR.
RandomForest and ExtraTrees show the steepest few-shot recovery: at 5% adaptation, RF gains +17.3 macro-
F1 pp and ET gains +19.4 pp, with FPR falling from 57.4%/62.1% to 24.9%/27.2%. Threshold recalibration at 
𝑡𝑡 𝑡 𝑡𝑡𝑡𝑡 is also useful for these ensembles (+7.4 pp for RF, +10.4 pp for ET). Drift-feature exclusion is counterpro-
ductive for RF but helps ET at 𝐾𝐾 𝐾 𝐾𝐾 (+5.1 pp, FPR 53.1%), suggesting different dependence on drifted features.
Logistic Regression benefits monotonically from drift-feature exclusion ( 𝐾𝐾 𝐾 𝐾𝐾: +9.8 pp; 𝐾𝐾 𝐾 𝐾𝐾: +10.2 pp; 
𝐾𝐾 𝐾 𝐾𝐾: +11.9 pp), consistent with a linear scorer whose additive weights are sensitive to benign-side feature shift. 
Few-shot retraining further improves LR to macro-F1 0.724 at 10%, although its upper bound remains the low -
est (0.870). MLP behaves less regularly: 𝐾𝐾 𝐾 𝐾𝐾 hurts, 𝐾𝐾 𝐾 𝐾𝐾 gives the largest drift-exclusion gain (+7.3 pp), and 
meaningful supervised recovery appears only at 10% adaptation (macro-F1 0.779, FPR 29.9%).
Cross-model comparison (Table 15). Few-shot retraining benefits all tabular probes, but tree ensembles 
recover fastest. At 10% adaptation, XGBoost achieves the highest F1 (0.878) and lowest FPR (10.3%), followed 
by RF (0.843, 18.9%) and ET (0.833, 20.8%), while MLP (0.779) and LR (0.724) trail. Similar full-hold-out 
upper bounds (0.870–0.922) indicate that the temporal gap is driven more by distribution shift and sample effi -
ciency than by model capacity alone.
Sequence models: temporal resilience with protocol-clean fine-tuning. BiLSTM and Transformer have 
stronger unadapted temporal baselines than tabular probes (macro-F1 0.799 and 0.775; FPR 20.8% and 14.6%).

Synthesis: complementary adaptation profiles. The results reveal two deployment profiles. Sequence mod-
els are more robust without adaptation ( +9.8 macro-F1 pp and −23.2 FPR pp over the best tabular baseline), 
whereas tabular tree ensembles are highly sample-efficient once a small labeled future-domain set is available 
(XGBoost gains +17.7 macro-F1 pp at 10% adaptation). The sequence fine-tuning results narrow this contrast: 
neural sequence probes also benefit from limited target labels, but their gains are smaller than XGBoost’s and 
BiLSTM remains more seed-sensitive than Transformer. Thus, adaptation efficiency is empirically separable 
from baseline temporal resilience and should guide long-term detector selection.
Threats to validity
Several limitations should be considered when interpreting the results. First, dynamic analysis observes only 
behavior triggered during the controlled 120-second execution window. Dormant, trigger-dependent, or environ-
ment-aware logic may remain unobserved, and we do not measure instruction- or method-level coverage. The 
parallel emulator protocol, fallback launch strategy, deterministic stimulation, Monkey interaction, and timeout 
handling reduce collection instability, but future work should quantify whether stimulation effectiveness differs 
across domains. The runtime-activity proxy statistics in Table 6 show that recent AndroZoo samples generate 
dense monitored traces, but they cannot prove that comparable fractions of application code or malicious payload 
logic were executed.
Second, all APKs are analyzed on a controlled Android 8.0 emulator. This stable longitudinal baseline supports 
Frida hooks, emulator reproducibility, and broad compatibility across the 2008–2026 timeline, but it may under-
represent behaviors tied to newer Android APIs or device configurations. A newer OS image could expose more 
modern API paths for recent applications while introducing backward-compatibility failures for older samples; 
some measured drift may therefore reflect interaction between ecosystem evolution and the fixed analysis envi -
ronment. Accordingly, the reported drift should be read as drift observed under a fixed Android 8.0 dynamic-
analysis environment. A multi-OS rerun using newer Android images would be required to quantify how much of 
the measured shift is caused by platform incompatibility rather than behavioral concept drift alone.
Third, VirusTotal consensus is an operational proxy rather than manual ground truth. We reduce label noise 
by excluding ambiguous low-positive samples and using conservative criteria (at least three positive engines for 
malware and zero positives for benign applications), but sensitivity analysis over stricter thresholds such as VT≥
5 remains necessary. The AndroZoo temporal hold-out is also balanced by design to isolate temporal generaliza-
tion and representation drift, not to estimate real-world prevalence; precision under low-prevalence deployment 
should be evaluated separately.
Fourth, the primary source-training experiments use a fixed seed for deterministic reproduction, whereas the 
sequence-adaptation analysis reports six-seed estimates with independent validation and untouched final testing. 
The six-seed estimates reduce the risk that the BiLSTM/Transformer fine-tuning conclusion is an artifact of one 
target split. The remaining limitation is that tabular adaptation is still reported from the original deterministic split 
and the upper-bound protocols differ across representation families: tabular upper bounds use five-fold Andro -
Zoo cross-validation, whereas sequence upper bounds use repeated 80/10/10 fine-tuning splits. In addition, the 
sequence 5% and 10% few-shot settings leave different final-test sizes after the fixed validation subset, so their 
comparison captures both adaptation-data effects and split sensitivity. Therefore, the adaptation study should still 
be interpreted as an operational sensitivity analysis rather than a complete hyperparameter-optimized continual-
learning benchmark.
Fifth, verified family labels are unavailable for all target samples, so the results should be interpreted as tem -
poral behavioral transfer rather than family-stratified attribution. The evaluated models are representative probes 
rather than exhaustively optimized detectors, which is intentional because the goal is to compare representation 
transfer under the same source-only protocol. Sequence traces are capped at 256 events; inspection shows this 
affects only 1.5% of AndroZoo benign traces and 0.4% of malware traces, but open-vocabulary encoders, longer

contexts, or semantic tag normalization may recover additional future-domain signal. Finally, the study uses one 
historical source domain and one recent temporal hold-out; larger longitudinal slices, family-aware stratifica -
tion, alternative VirusTotal thresholds, additional seeds, and additional temporal datasets would clarify whether 
the observed drift patterns are monotonic, family-specific, or concentrated in particular application categories. 
Because the behavior-category labels are produced consistently by the instrumentation taxonomy, the category-
level drift results are more reliable than an inferred malware-family analysis would be for the present data.
Conclusion
This paper presented DriftDroid, a temporal behavioral drift study for Android malware detection. Rather than 
proposing a new detector architecture, the work evaluates how historical runtime-behavior evidence transfers to 
recent Android applications. KronoDroid is used as the historical source domain, while a 2024–2026 AndroZoo 
hold-out selected with explicit VirusTotal criteria provides the future-domain evaluation setting. This design 
separates source-domain learning from temporal generalization and avoids using future samples during prepro -
cessing, model selection, or thresholding.
The empirical results show that temporal drift is both measurable and operationally significant. Source-domain 
validation produces strong results for both sequence and tabular probes, but all models degrade on the future-
domain hold-out. The degradation is representation dependent. Sequence models retain the strongest temporal 
performance, with the BiLSTM reaching 0.7988 macro-F1 on AndroZoo and the Transformer retaining the high-
est AndroZoo ROC-AUC among the evaluated probes. Tabular models, despite strong KronoDroid validation 
scores, degrade more sharply; their dominant error mode is a high false-positive rate on recent benign applica -
tions. This indicates that aggregate behavioral indicators learned from historical data can become unreliable as 
benign applications increasingly exhibit network, file, cryptographic, SDK, and background-service behaviors 
that previously looked suspicious.
As a secondary operational analysis, the adaptation experiments show that drift is not easily remedied by 
post-hoc adjustments and that the two model families respond differently when limited recent-domain evidence 
becomes available. Applied across all five tabular probes, drift-feature exclusion is generally ineffective for tree 
models (the most-drifted features are simultaneously the most discriminative), while conservative threshold reca-
libration is effective for RandomForest and ExtraTrees (+7.4 and +10.4 macro-F1 pp respectively in post-hoc 
threshold sweeps). Few-shot supervised retraining consistently bridges the gap for all tabular models at the 10% 
adaptation setting: macro-F1 increases by 14–22 pp across architectures, closing 48–80% of the performance 
gap to the full-retrain upper bound (72–80% for tree-ensemble probes; MLP and LR recover more modestly at 
62% and 48% respectively, consistent with the greater inertia of neural and linear representations under small-set 
retraining). Sequence models present the complementary profile: their event-order representations are inher -
ently more robust to benign-side drift (+9.8 macro-F1 pp and −23.2 FPR pp over the best tabular baseline without 
any adaptation), and the six-seed fine-tuning protocol improves mean macro-F1 over the unadapted baselines 
for both sequence probes. BiLSTM improves to 0.835±0.009 macro-F1 with 5% adaptation and 0.823±0.024 
with 10%, while Transformer improves to 0.804±0.006 and 0.818±0.004. These results no longer support a 
simple catastrophic-forgetting interpretation; instead, they indicate beneficial but seed-sensitive neural adapta -
tion, especially for BiLSTM. The primary evidence therefore remains the clean unadapted temporal evaluation 
and the behavioral drift analysis: robust Android malware evaluation requires explicit temporal hold-outs and 
representation-aware drift analysis, while long-term detector reliability will likely require mechanisms to incor -
porate recent-domain evidence.
Future work should explore several directions to extend these findings. First, drift-aware feature regularization 
during source-domain training—penalizing reliance on features with high benign-side JSD—could improve tem-
poral robustness without requiring future-domain labels. Second, temporally invariant behavioral representations 
that explicitly separate stable malware-indicative patterns from evolving benign SDK behaviors may reduce the

aggregate feature aging observed here; a direct TIF-style or invariant-risk baseline on the same dynamic features 
would be a natural next comparison. Third, semantic normalization for future-domain sequence tags  should be 
evaluated to determine whether open-vocabulary or API-ontology encoders can retain the strict temporal protocol 
while reducing the information loss caused by UNK mapping. Fourth, rehearsal-based continual fine-tuning and 
regularized neural updating should be evaluated for sequence models to determine whether target-domain gains 
can be improved while preserving source-domain behavior. Fifth, longitudinal drift analysis  across multiple 
annual slices, Android platform versions, and VirusTotal threshold settings would clarify whether the behavioral 
shifts observed here are monotonic, accelerating, environment-sensitive, or concentrated around specific Android 
API transitions.
